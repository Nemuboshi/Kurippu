# Kurippu 桌面端迁移到 C# + Avalonia

日期：2026-10-22
状态：已批准实施；发行切换仍取决于四平台验收

## 意图

Kurippu 现有功能基本可用，但 Electron 的主进程、preload、renderer、Node 原生插件和跨平台资源打包使开发与维护过于复杂。迁移的首要目的，是让项目结构和依赖边界更明晰，而不是追求某个安装包大小。用户接受重写现有 Svelte 界面及 TypeScript 业务逻辑，也接受首版不保留 Windows/macOS 的共享纹理渲染路径。

这是现有桌面应用的移植，不是产品改版。迁移期间 Electron 版本保持可用，直到四个平台的新版本达到验收条件。

## 目标与范围

- 使用 C# + Avalonia 实现桌面 UI、应用状态和业务服务，消除运行时的 Electron/Node、preload/IPC 和 N-API 插件层。
- 保持现有用户可见的工作流：本地文件或 URL 输入、媒体探测、预览及播放控制、轨道和裁剪/效果/编码参数、测试及正式导出、进度/日志/取消、输出文件操作。
- FFmpeg 作为随安装包分发的独立可执行文件，由 C# 以参数数组启动；libmpv 作为随包分发的原生库，经薄封装调用。yt-dlp 保持当前的可选外部工具行为，不在本次迁移中新增捆绑要求。
- 首版同时交付现有四个目标：Windows x64、macOS x64、macOS arm64、Linux x64。构建成功不等于交付成功；每个目标均须实际启动并完成播放、导出和打包冒烟验证。
- 保持现有功能语义和尽可能相近的交互布局；不要求逐像素复刻，但不能借迁移删减功能或改变默认编码行为。

## 非目标与反目标

- 不增加 Android、iOS、Web、其他 CPU 架构或新的视频功能。
- 不把 FFmpeg CLI 改写成 libav* 的托管绑定，也不要求将 yt-dlp 捆绑进安装包。
- 不以 Native AOT、单文件发布、极限裁剪、绝对安装包大小或共享纹理零拷贝作为首版验收条件。先用常规自包含发布建立稳定基线，再测量和优化体积。
- 不在迁移中同步进行 UI 重设计、编码策略变更或大规模领域重构。
- 不能用“代码变成 C#”掩盖复杂度：禁止重新造一个通用消息总线、动态插件框架或难以追踪的全局服务容器。

## 当前系统基线

- `src/renderer/App.svelte` 组织 source -> info -> encoder 流程；`src/renderer/Source.svelte` 包含本地文件/拖放和依赖外部 yt-dlp 的 URL 下载。
- `src/renderer/player/Player.svelte` 及相关组件负责播放、选轨、片段标记、裁剪、键盘控制；`src/renderer/player/mpv-video.ts` 经 preload/IPC 与 `src/main/mpv-service.ts`、`native/mpv/src/mpv_addon.cc` 交互。当前有软件帧路径，Windows/macOS 另有共享纹理路径。
- `src/engine` 负责选项派生、校验、尺寸/码率、FFmpeg 参数、进度、输出路径等；`src/renderer/encode/runner.svelte.ts` 负责测试编码、单/双 pass、预览拼接、取消和日志。
- `src/main` 和 `src/preload` 包含进程、对话框、临时文件、文件/系统操作及边界校验；这些能力在新的同进程桌面应用中改为直接调用的服务，不照搬 IPC 形状。
- `scripts/fetch-binaries.ts`、`scripts/libmpv-runtime.ts` 和 `.github/workflows/build.yml` 处理 FFmpeg 下载、libmpv 依赖收集/修补及四目标 CI。迁移后仍需为每个平台处理原生依赖、加载路径和 macOS 签名相关事项。
- 当前仓库没有可测量的构建产物；不能据此断言迁移会节省多少 MB。开始实施前保留旧版功能用例和各平台产物体积作为对照。

## 设计

### 模块边界

1. **Kurippu.App**：Avalonia 视图和视图模型，负责用户交互与状态展示。视图不拼接 FFmpeg 命令，不直接 P/Invoke，也不拥有进程生命周期。
2. **Kurippu.Core**：媒体信息、选项派生、校验、时间/尺寸/码率计算、FFmpeg 参数生成、导出工作流和输出命名。保持与 UI、平台 API 和具体进程启动方式分离。按现有测试用例移植行为，避免借机“修正”未确认的语义。
3. **Kurippu.Media**：libmpv 的最小托管互操作及播放器服务，暴露打开、播放/暂停、定位、音量、选轨、属性、事件和帧更新；使用确定性的资源释放，集中处理线程/回调与错误。媒体探测的输出模型供播放器和编码选项共用。
4. **Kurippu.Platform**：FFmpeg/yt-dlp 可执行文件解析与启动、取消和日志流、对话框、文件系统、临时文件、打开文件/所在目录、平台资源路径。接口只围绕实际用例设立，不复刻 Electron IPC 通道。
5. **Packaging/CI**：按目标 RID 选择并携带 FFmpeg、libmpv 和非系统的原生依赖；在干净机器/runner 上验证加载，而不依赖开发机的 Homebrew、apt 或 PATH。可在构建机安装 SDK，但安装后的应用不得要求用户手工安装它们。yt-dlp 是明示的例外。

项目/程序集的精确拆分由实施计划决定；上述是依赖方向，而非必须创建五个程序集。Core 不依赖 App 或 Platform；应用组合具体服务。平台差异局限在资源/加载和必要的渲染适配器中。

### 视频预览

首版优先使用 libmpv 的软件帧输出，交给 Avalonia 控件呈现，并将帧转换/复制与 UI 线程更新隔离。必须测量实际预览的流畅度、CPU/内存占用、缩放、音画同步和退出/切换文件时的资源释放；不能只以“画面出现”作为成功。先在四个平台验证此路径，再决定是否需要引入 Avalonia 的 GPU 资源导入或平台专用渲染。

播放器服务不向视图暴露 mpv 指针或平台句柄。若软件路径在任一目标无法达到可接受的日常预览体验，先记录瓶颈并做针对性的 GPU/原生渲染试验；不要默默降低分辨率或删除播放功能。具体性能阈值以旧版同一测试素材的实际体验为比较基线，由实施阶段记录并提交给用户确认。

### 编码与外部进程

保留 FFmpeg 命令行路径，以现有 `src/engine` 测试和代表性输入/选项的参数快照作行为对照。C# 进程服务负责安全传参、标准输出/错误流、取消及进程树收尾；导出工作流负责测试编码、单/双 pass、预览拼接、进度、输出和临时文件清理。跨平台路径引用、滤镜转义和 concat 文件内容须以真实样本回归，不采用 shell 字符串拼接。

URL 流程保持外部 yt-dlp 的发现、格式选择、下载进度/取消与失败提示；未安装时仍能使用本地文件和编码。不要把“FFmpeg 随包分发”误写成“yt-dlp 随包分发”。

### 分发

四个目标分别发布，不把所有平台二进制放进同一个安装包。使用锁定的 SDK、NuGet 和原生二进制来源；记录版本及获取方式，避免不受控的 latest 资源改变构建内容。对每个产物记录安装包大小及解压/安装后大小，作为观察指标而非验收门槛。macOS 的动态库路径与签名、Linux 的运行库/RPATH、Windows DLL 搜索路径必须在打包后的进程中验证。

Avalonia 自包含发布、P/Invoke 和 GPU composition 均有官方支持，但具体 libmpv 渲染集成仍是本项目的工程风险，不能当作现成播放器控件。参考：[Avalonia 原生互操作](https://docs.avaloniaui.net/docs/app-development/native-interop)、[自定义渲染](https://docs.avaloniaui.net/docs/graphics-animation/custom-rendering)、[Native AOT](https://docs.avaloniaui.net/docs/deployment/native-aot)。

## 迁移顺序与验收

1. **建立可比较的基线**：从旧版提取操作清单和现有测试的预期，准备含不同格式、音/字幕轨、非 ASCII 路径及失败情况的小型测试素材；记录四个平台旧版的播放/导出表现与包大小。素材来源和许可由实施者处理。
2. **四平台技术试验**：最小 Avalonia 窗口加载随包 libmpv，打开/播放/定位/关闭同一素材；执行随包 FFmpeg 的短导出；发布、安装或解包后在四目标运行。验证原生依赖闭包、帧渲染和生命周期。若任一目标失败，先解决该目标，不继续大规模移植 UI。
3. **移植领域行为和工作流**：先移植 Core 的确定性函数及对应测试，再移植播放器/进程服务与状态管理，最后逐步移植 source、info、player、编码选项和导出界面。旧版在此期间不移除。
4. **功能对照和打包**：用同一素材/选项比较媒体探测、参数、输出、取消和错误路径；在四个目标从最终产物完成冒烟验证。记录无法一致的差异并明确批准，不以“技术栈已替换”代替验收。
5. **切换与清理**：只有四平台门槛通过且用户认可行为差异后，才将 Avalonia 版本设为默认发行，移除旧的 Electron 构建链和不再使用的 N-API/IPC/前端源文件；保留可追溯的回退标签/版本。

验收至少包括：本地文件/拖放打开；URL 流程在有/无 yt-dlp 时的行为；媒体信息和轨道选择；播放、暂停、定位、片段/裁剪操作；主要视频/音频/字幕选项；测试导出、单/双 pass、预览拼接、进度、取消和输出打开；无效参数/缺失工具/异常退出；连续切换文件及关闭时无残留 FFmpeg/mpv 进程或资源。自动测试覆盖领域计算和进程编排，最终产物上的人工或自动冒烟覆盖每个目标。

## 风险与留给实施者的决定

- 软件帧上传可能在高分辨率或高帧率素材上成为瓶颈；四平台技术试验是继续完整迁移的闸门。具体渲染 API、缓冲复用和后续 GPU 路线交给实施者实测选择。
- libmpv 的传递依赖和 FFmpeg 构建来源决定包大小、兼容性和分发义务；需要独立盘点，不能因去掉 Electron 而忽略。二进制具体版本与提供方由实施者在计划中验证并固定。
- macOS 两架构、Linux 发行版兼容范围及系统库假设沿用当前发布目标，不扩大支持承诺；记录 CI runner 与目标系统上的差异。
- Avalonia/.NET 的具体稳定版本、XAML/MVVM 库、安装器和解决方案目录命名由实施者在计划阶段选定，以最少依赖和四平台可验证性为准。
- 如果技术试验不能在四平台形成可维护且可接受的播放体验，暂停全面重写，向用户报告证据和替代路线；不要投入完整 UI 后才发现渲染路线不可行。
